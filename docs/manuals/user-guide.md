# Eazy Test Web 用户使用手册

## 1. 这份手册怎么用

这份手册面向真实使用者，不讲架构推演，重点回答三件事：

1. 你第一次上手应该怎么跑通主链路。
2. 你日常怎么维护测试资产、执行回归、看报告、排故障。
3. AI Copilot 在哪里提效，边界又在哪里。

如果你更关心项目背景、部署方式或环境治理，请继续阅读：

- [项目介绍手册（归档）](../archive/manuals/project-overview.md)
- [配置与环境治理](./environment-governance.md)
- [执行链路可靠性](./execution-reliability.md)
- [部署拓扑](./deployment-topology.md)

## 2. 产品一句话

Eazy Test Web 是一套把测试资产、执行过程、调度能力、报告结果和 AI 辅助统一收口到浏览器里的 API 测试平台。

你可以把它理解成一条完整链路：

`项目 -> 套件 -> 用例 -> 环境 -> 执行 -> 报告 -> 复盘`

## 3. 首次上手

### 3.1 使用前确认

第一次使用前，请先确认：

1. API 服务已启动。
2. 你已经有可登录账号。
3. 如果要执行 `suite`，worker 已启动。
4. 如果要使用定时任务，scheduler 已启动。
5. 如果用例含脚本型 Processor，运行环境能找到 Node.js。

相关命令：

```powershell
python -m requesttool serve --reload
python -m requesttool worker
python -m backend.scheduler
```

访问入口：

- Web：`http://127.0.0.1:8000/`
- API 文档：`http://127.0.0.1:8000/docs`

### 3.2 第一次跑通主链路

推荐严格按这个顺序走一遍：

1. 登录系统。
2. 进入“工作台”，创建一个项目。
3. 在项目下创建一个套件。
4. 在“环境配置”里创建一个环境，填好 `Base URL`。
5. 回到“工作台”，创建一条用例。
6. 至少补齐请求方法、URL、Headers、Body 和最小核心断言。
7. 进入“执行中心”，先执行单条 `case`。
8. 打开执行详情，确认请求、响应和断言结果。
9. 进入“报告归档”，查看生成的 HTML 或 JSON 报告。

这条链路是当前版本最稳的最小闭环。

## 4. 页面地图

### 4.1 指挥台

适合看全局状态：

- 最近执行
- 资产规模
- 质量态势
- 报告与风险信号

日常值班、回归日巡检，先看这里。

### 4.2 工作台

这是主工作区，负责管理：

- `Project`
- `Suite`
- `Case`
- AI Copilot 设计与编写能力
- Excel / 历史资产导入

如果你日常是测试设计、用例维护、AI 辅助生成，这里是主战场。

### 4.3 环境配置

这里管理运行时上下文：

- `Base URL`
- 公共请求头
- 环境变量

原则很简单：环境差异放这里，不要硬编码进用例。

### 4.4 执行中心

这里负责：

- 发起单用例执行
- 发起套件执行
- 查看执行状态
- 失败筛选
- 取消与重试
- 打开执行详情
- 对失败执行做 AI 诊断

### 4.5 定时任务

这里负责把“手工点执行”升级成“可审计的调度资产”。

当前定时任务只绑定：

- 一个 `suite`
- 一个可选 `environment`
- 一条 `cron` 规则

它只负责创建待执行任务，真正跑用例的仍然是 worker。

### 4.6 报告归档

这里查看和沉淀执行产物：

- HTML 报告
- JSON 报告
- AI 总结
- 归档结果

### 4.7 审计日志

仅 `admin` 可见，用于追踪关键操作和资源变更。

### 4.8 用户管理

仅 `admin` 可见，用于管理账号、角色和启停状态。

## 5. 核心对象怎么理解

| 对象 | 作用 | 最常见场景 |
| --- | --- | --- |
| `Project` | 顶层业务容器 | 按系统、业务域收口测试资产 |
| `Suite` | 一组可一起维护、一起回归的用例集合 | 按链路或模块组织回归集 |
| `Case` | 最小执行单元 | 编写请求、断言、处理器和元数据 |
| `Environment` | 运行时上下文 | 切换地址、公共头、环境变量 |
| `Execution` | 一次真实运行记录 | 追踪状态、失败明细、重试信息 |
| `Report` | 执行产物 | 复盘、归档、对外同步结果 |
| `Scheduled Job` | 自动触发规则 | 每日冒烟、工作日回归 |

一句话记忆：

- `Project` 决定资产放哪
- `Suite` 决定怎么组织
- `Case` 决定测什么
- `Environment` 决定在哪测
- `Execution` 决定跑得怎样
- `Report` 决定怎么沉淀结果
- `Scheduled Job` 决定什么时候自动跑

## 6. 日常操作手册

### 6.1 创建项目

1. 进入“工作台”。
2. 点击新增项目。
3. 填写项目名称和说明。
4. 保存。

建议按业务域或系统边界建项目，不要把所有内容堆进一个项目。

### 6.2 创建套件

1. 在“工作台”切到套件区域。
2. 选择所属项目。
3. 填写名称和说明。
4. 保存。

推荐把一组能一起回归的链路放进同一套件。

### 6.3 创建用例

1. 在“工作台”新增用例。
2. 选择所属套件。
3. 填写请求方法与 URL。
4. 配置 `Headers` 和 `Body`。
5. 补齐 `Assertions`。
6. 按需补充 `Processors` 和 `Metadata`。
7. 保存。

建议先把核心主链路写对，再用 AI 做补强，不要一上来全靠生成。

### 6.4 配置环境

1. 进入“环境配置”。
2. 创建环境。
3. 填写 `Base URL`。
4. 配置公共 Header。
5. 配置环境变量。

以下内容建议放进环境，而不是写死在用例里：

- 服务地址
- Token / 鉴权头
- 租户标识
- 按环境变化的参数

### 6.5 执行单条用例

适合快速验证和精准排错。

1. 进入“执行中心”。
2. 选择 `case`。
3. 选择目标用例。
4. 选择环境。
5. 发起执行。
6. 打开执行详情查看结果。

### 6.6 执行整个套件

适合日常回归和批量验证。

1. 进入“执行中心”。
2. 选择 `suite`。
3. 选择目标套件。
4. 选择环境。
5. 发起执行。
6. 在列表页观察状态流转。

注意：`suite` 执行依赖独立 worker，若一直停在排队中，先检查 worker 是否在线。

### 6.7 查看执行详情

推荐按这个顺序看：

1. 先看执行状态和通过率。
2. 再看失败拆解和首个失败点。
3. 然后看单条执行项的原始请求、响应、断言。
4. 最后再看 AI 诊断结果。

别反过来。先看原始事实，再看 AI 解释。

### 6.8 查看和使用报告

1. 进入“报告归档”。
2. 选择目标报告。
3. 在线预览或新标签页打开。
4. 如需业务摘要，生成 AI 总结。
5. 审核后再应用总结。

### 6.9 创建定时任务

适合每日冒烟、工作日回归、固定时间段巡检。

1. 进入“定时任务”。
2. 点击“新建任务”。
3. 选择项目、套件和可选环境。
4. 填写任务名称与说明。
5. 输入 `cron` 表达式。
6. 选择时区。
7. 选择并发策略和补偿策略。
8. 保存并启用。

推荐默认：

- 并发策略：`forbid`
- 补偿策略：`skip`

这两个组合最稳，最不容易制造重复执行。

### 6.10 查看定时任务运行记录

1. 在“定时任务”页打开某条任务。
2. 点击“运行记录”。
3. 查看计划时间、触发时间、状态和关联的 `Execution`。

如果任务有触发记录但没有跑起来，先去“执行中心”看对应 execution 是否还在 `pending`。

## 7. 导入历史资产

### 7.1 Excel 导入

适合从手工台账快速收口到平台：

1. 进入“工作台”。
2. 选择目标项目。
3. 上传 Excel。
4. 导入后抽样检查关键用例。
5. 再补环境、断言和执行验证。

### 7.2 旧版 `project.json` 导入

适合从历史桌面端迁移：

1. 先创建目标项目。
2. 导入 `project.json`。
3. 抽样执行核心用例。
4. 用报告校验迁移质量。
5. 再用 AI 做补强。

## 8. AI Copilot 怎么用

### 8.1 先讲边界

平台里的 AI 是 `Copilot`，不是 `Autopilot`。

它负责：

- 生成建议
- 补充覆盖面
- 辅助归因
- 帮你压缩汇报成本

它不负责：

- 直接替你做最终测试判断
- 静默改写核心执行结果
- 绕过人工确认直接落库

### 8.2 AI 能做什么

| 阶段 | AI 能力 | 入口 |
| --- | --- | --- |
| 测试设计 | 覆盖率扫描 | 工作台 |
| 测试设计 | 测试点生成 | 工作台 |
| 用例生成 | 用例草稿生成 | 工作台 |
| 用例编写 | 断言建议 | 用例编辑区 |
| 用例编写 | AI 测试数据 | 用例编辑区 |
| 用例编写 | AI Mock 模板 | 用例编辑区 |
| 执行前 | AI 预执行准备 | 用例编辑区 |
| 排障 | AI 失败诊断 | 执行详情 |
| 汇报 | AI 总结 | 报告详情 |
| 协作 | AI Chat | 全局入口 |

### 8.3 推荐使用顺序

最稳的方式不是“让 AI 一把梭”，而是：

1. 人先写 1 到 3 条最核心主链路。
2. 用 AI 补断言和边界测试数据。
3. 用覆盖率扫描和测试点生成查漏补缺。
4. 需要时生成用例草稿批量导入。
5. 执行后再用 AI 做失败诊断和报告总结。

### 8.4 AI 测试数据和 AI Mock 的正确用法

这两个能力不会静默改掉你正在编辑的请求体。

正确流程是：

1. 先生成并保存 AI 产物到 case metadata。
2. 再在“AI 预执行准备”里显式选择这次要带哪些 variant 或 template。
3. 执行完成后，在结果里查看本次 preparation 摘要。

这个设计是为了让 AI 产物可回溯、可选择、可复用，而不是一次生成后把原始用例污染掉。

## 10. 常见问题

### 10.1 套件一直停在排队中

通常是 worker 没启动。

```powershell
python -m requesttool worker
```

### 10.2 定时任务不触发

通常先检查 scheduler：

```powershell
python -m backend.scheduler
```

然后再看该任务是否已启用、`next_run_at` 是否已计算出来。

### 10.3 我能看页面但不能编辑

大概率是当前账号是 `developer`，该角色默认偏只读。

### 10.4 为什么 AI 没直接改掉我的用例

这是产品设计，不是 bug。

平台故意把 AI 放在“建议层”和“辅助层”，避免误改核心测试资产。

### 10.5 为什么 AI 测试数据或 AI Mock 应用后，请求体没变

因为它们先写入的是 case metadata，只有在“AI 预执行准备”里显式选择后，才会参与本次执行。

### 10.6 为什么环境里的 `123` 会变成 number

环境变量按 JSON 字面量解析：

- `123` 会被当成 number
- `true` 会被当成 boolean
- `"tenant-a"` 会被当成 string

如果你希望它始终是字符串，请显式加引号。

## 11. 推荐工作流

### 11.1 从零开始建立一套测试

1. 创建项目。
2. 创建套件。
3. 创建环境。
4. 先手工写核心用例。
5. 跑通单条 `case`。
6. 用 AI 补断言和测试数据。
7. 用覆盖率扫描补剩余缺口。
8. 跑 `suite` 回归。
9. 用报告和 AI 总结做复盘。

### 11.2 从历史资产迁移到平台

1. 创建目标项目。
2. 导入 Excel 或 `project.json`。
3. 抽样执行核心用例。
4. 用报告校验迁移质量。
5. 再逐步接入 AI 和调度能力。

### 11.3 做一次高效失败排查

1. 在执行中心筛选失败记录。
2. 先看原始请求/响应/断言。
3. 再看失败分类和首个失败点。
4. 然后生成 AI 诊断。
5. 回到用例、环境或依赖侧修复。
6. 重跑验证。
7. 用报告总结收口复盘。

## 12. 当前版本边界

- 默认开发数据库仍偏本地场景
- 历史导入能力仍是迁移桥接能力
- 定时任务只负责入队，不直接执行用例
- `replace` / `fire_once` 应视作谨慎使用策略
- AI 仍是辅助决策层，不替代确定性执行规则
