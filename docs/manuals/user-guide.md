## 1. 这份手册给谁看

## 2. 产品一句话

Eazy Test Web 是一个面向团队协作的 Web-first API 测试平台。

它把原来分散在个人机器上的测试资产、执行过程、报告产物和 AI 辅助能力，统一收口到浏览器里，形成一条完整链路：

`项目 -> 套件 -> 用例 -> 环境 -> 执行 -> 报告 -> 复盘`

## 3. 快速上手

### 3.1 访问入口

- Web 页面：`http://127.0.0.1:8000/`
- API 文档：`http://127.0.0.1:8000/docs`

如果前端已构建完成，后端会直接托管 `frontend/dist`，访问根路径即可进入系统。

### 3.2 使用前确认

第一次使用前，先确认这几件事：

1. 你已经有可登录账号
2. 后端服务已经启动
3. 如果要执行套件，`worker` 已经启动
4. 如果要使用脚本型处理器，本机可以找到 `Node.js`

套件执行依赖独立 worker：

```powershell
python -m requesttool worker
```

如果系统找不到 `node`，可以显式配置：

```env
REQUESTTOOL_NODE_BIN=/absolute/path/to/node
```

### 3.3 第一次跑通主链路

建议按下面顺序跑通一次：

1. 登录系统
2. 进入“工作台”，创建项目
3. 在项目下创建套件
4. 在套件下创建一条 API 用例
5. 进入“环境”，创建测试环境并填写 `Base URL`
6. 进入“执行”，先跑单条用例
7. 进入“报告”，查看 HTML 或 JSON 报告

这是当前版本最稳定、最容易理解的使用路径。

## 4. 系统里最重要的 4 个对象

| 对象 | 作用 | 典型内容 |
| --- | --- | --- |
| 项目 `Project` | 业务或系统边界 | 一个服务域、一个业务线、一组接口域 |
| 套件 `Suite` | 一组可一起维护和执行的用例集合 | 登录链路、订单链路、回归集 |
| 用例 `Case` | 最小执行单元 | Method、URL、Headers、Body、Assertions、Processors |
| 环境 `Environment` | 运行时上下文 | Base URL、公共请求头、环境变量 |

一句话理解：

- 项目是容器
- 套件是组织方式
- 用例是最小执行单元
- 环境是运行时上下文

## 6. 测试提效点

这一节不讲“有什么功能”，只讲“为什么能更快”。

### 6.1 资产集中化，减少重复搭建

- 用例、环境、报告都沉淀在平台里，不再散落在个人机器
- 团队成员直接复用已有项目和套件，避免重复造轮子
- 环境级公共头和变量可以复用，减少每条用例重复填写

### 6.2 结构化编辑，减少低质量脚本

- 请求头、请求体、断言都有结构化编辑器
- 能用结构化断言表达的逻辑，不需要先写脚本
- 这会直接降低维护成本和误改风险

### 6.3 单条验证 + 套件回归的双链路

- 单用例适合快速试错和本地验证
- 套件执行适合回归和批量验证
- 两条链路拆开后，定位问题更快，不会一上来就把整套回归跑成黑盒

### 6.4 Worker 解耦执行，减少长请求阻塞

- 套件执行通过 worker 消费队列
- 执行链路和页面请求解耦
- 更适合后续扩展重试、并发和长时间回归任务

### 6.5 报告在线预览，减少找文件成本

- 报告可直接在页面预览、下载、打开新标签
- 不再需要手动登录服务器、翻目录、找输出文件
- HTML 适合展示，JSON 适合排查和二次处理

### 6.6 导入能力降低迁移成本

- Excel 导入适合快速把台账转成平台资产
- `project.json` 导入适合旧桌面端迁移
- 团队能在不推倒重来的前提下逐步切到 Web 体系

## 7. AI 应用点

AI 在这个平台里的定位是：

- 负责提出建议、补全信息、帮助归因、帮助总结
- 不负责最终判定、最终落库、最终执行结果裁决

也就是说，AI 是 Copilot，不是 Autopilot。

### 7.1 AI 能力总览

| AI 场景 | 入口位置 | 解决什么问题 | 用户动作 |
| --- | --- | --- | --- |
| 覆盖率扫描 | 工作台 | 发现项目或套件的覆盖缺口 | 扫描后查看缺口和建议测试点 |
| 测试点生成 | 工作台 AI 设计器 | 把覆盖缺口或 Markdown 文档转成测试点 | 选择测试点，生成草稿 |
| AI 用例草稿 | 工作台 AI 设计器 | 批量生成可审阅的用例草稿 | 审核后导入套件 |
| 断言建议 | 用例编辑区 | 为当前用例补关键断言 | 追加应用或覆盖应用 |
| AI 测试数据 | 用例编辑区 | 生成 payload 变体和建议断言 | 选择后写入 metadata |
| AI Mock | 用例编辑区 | 生成可导出的 Mock 模板 | 选择后写入 metadata |
| AI 预执行准备 | 用例编辑区 | 把 test data / mock 作为本次执行参数带入 | 选择 variant/template 后执行 |
| AI 诊断 | 执行详情 | 归纳失败原因与下一步动作 | 生成、查看历史、复制建议 |
| AI 总结 | 报告详情 | 产出业务摘要、风险摘要、行动建议 | 生成后应用到报告 metadata |

### 7.2 AI 设计阶段怎么用

适合场景：

- 新项目刚建好，不知道哪些点还没覆盖
- 手上有 Markdown 接口文档，想快速生成测试点
- 想先做 test design，再决定哪些点真正落成用例

推荐流程：

1. 先在工作台选定项目或套件
2. 使用“AI 覆盖率扫描”看 coverage 缺口
3. 把建议点带入“测试点提示”
4. 可选上传 Markdown 文档，再补充提示词
5. 生成测试点预览
6. 选择合适的测试点
7. 基于测试点生成草稿
8. 审批并导入套件

当前 AI 设计器支持：

- `balanced`：平衡覆盖
- `smoke`：Smoke 优先
- `negative`：负向优先
- `boundary`：边界优先

也支持追加自定义提示，例如：

```text
登录接口必须覆盖 token 失效场景。
```

### 7.3 AI 编写阶段怎么用

#### AI 断言

适合你已经把请求写出来，但断言不完整的场景。

建议：

- 先人工保留最小核心断言
- 再用 AI 补充容易漏掉的状态码、Header、JSONPath 断言
- 应用时优先使用“追加”，只有在你确认旧断言质量差时再用“覆盖”

#### AI 测试数据

适合你想让一条用例快速扩展出多个数据变体的场景。

平台会给出：

- 数据变体
- 目标字段
- 变体原因
- 建议断言

注意：

- 应用后写入的是 case metadata
- 不会直接改写你当前编辑中的请求体

#### AI Mock

适合提前准备依赖接口的响应模板，或导出给其他系统复用的场景。

平台会给出：

- 模板名
- 命中规则
- 状态码
- 响应模板

注意：

- 当前阶段管理的是 Mock 模板，不是运行时 Mock 平台
- 应用后同样是写入 case metadata

### 7.4 AI 运行阶段怎么用

#### AI 预执行准备

这是 Phase 4 的核心能力。

它的价值不是“改写用例”，而是“把已保存的 AI 产物作为本次执行的显式准备参数带入”。这样做的好处是：

- 用例本体保持稳定
- 不同 test data / mock 组合可以多次试验
- 每次执行使用了什么准备参数，可以追溯

当前做法是 case-first：

- 先在用例里应用或保留 AI 测试数据 / AI Mock
- 再在“AI 预执行准备”里选择本次执行要带入哪些 variant / template
- 最后发起执行

#### AI 诊断

适合执行失败后做第一轮归因。

平台会输出：

- 诊断分类
- 根因假设
- 置信度
- 下一步动作建议

建议用法：

1. 先看原始失败详情
2. 再用 AI 诊断帮助归纳
3. 最后回到请求、响应、断言详情做人工确认

#### AI 总结

适合把技术报告转成更容易给业务、研发负责人或项目经理阅读的摘要。

平台会输出：

- `executive_summary`
- `risk_summary`
- `top_failures`
- `recommended_actions`

你可以只看、复制，也可以把它应用到报告 metadata 中，形成带摘要的报告资产。

### 7.5 AI 历史、回放和可追溯

当前 AI 能力不是一次性弹窗，而是有历史和追踪能力的：

- 测试点有历史
- 用例草稿有历史
- 测试数据和 Mock 有历史
- 诊断有历史
- 产物之间支持 lineage 查看

这意味着：

- 你可以回看之前 AI 给过什么建议
- 你可以把历史结果重新加载为当前预览
- 你可以在团队复盘时解释“这次建议从哪来、后来怎么被采用”

## 8. 推荐使用方式

### 8.1 从零开始建设一套接口测试

1. 创建项目
2. 创建套件
3. 创建环境
4. 先手工创建 1 到 3 条核心用例
5. 跑通单用例执行
6. 用 AI 断言和 AI 测试数据补强关键用例
7. 用覆盖率扫描和测试点生成扩展剩余用例
8. 批量导入 AI 草稿
9. 跑套件回归
10. 通过报告和 AI 总结做结果复盘

### 8.2 从旧资产迁移到平台

1. 先创建目标项目
2. 通过 Excel 或 `project.json` 导入历史资产
3. 先抽样跑几条核心用例
4. 用报告核对迁移结果
5. 再用 AI 补断言、补测试数据、补测试点

### 8.3 做一次高效的失败排查

推荐顺序：

1. 执行页筛选失败记录
2. 打开执行详情看失败项
3. 查看请求、响应、断言结果
4. 生成 AI 诊断
5. 根据建议回到用例、环境或依赖侧修改
6. 重试执行
7. 在报告页生成 AI 总结，输出复盘结论

## 9. 页面说明

### 9.1 概览

适合快速判断当前工作区状态：

- 项目数、套件数、用例数、环境数
- 执行成功率
- 进行中执行数
- 最近执行
- 最新报告

### 9.2 工作台

工作台是测试资产维护中心，包含项目、套件、用例三部分。

你可以在这里完成：

- 项目、套件、用例维护
- Excel 导入
- 旧版桌面端数据导入
- AI 覆盖率扫描
- AI 测试点设计
- AI 草稿导入
- 用例级 AI 断言、AI 测试数据、AI Mock、AI 预执行准备

### 9.3 环境

环境页负责维护运行上下文：

- `Base URL`
- 公共请求头
- 环境变量

建议把会变化的地址、鉴权头、租户号等都放到环境，而不是硬编码进每条用例。

### 9.4 执行

执行页是运行中心，支持两种执行：

- `case`：单用例即时执行
- `suite`：套件排队执行

你可以在这里：

- 发起执行
- 搜索和筛选执行记录
- 只看失败执行
- 取消正在运行的套件执行
- 对历史执行发起重试
- 查看执行详情
- 生成 AI 诊断

### 9.5 报告

报告页负责集中管理历史执行产物。

当前支持：

- HTML 报告
- JSON 报告
- 在线预览
- 新标签打开
- 下载
- AI 总结

### 9.6 审计日志

仅 `admin` 可见。

适合排查：

- 谁改了什么
- 谁触发了什么动作
- 某次 AI 或执行相关动作是谁发起的

### 9.7 用户管理

仅 `admin` 可见。

适合做协作账号治理和角色分配。

## 11. 常见问题

### 11.1 为什么套件一直停在排队中

因为套件执行依赖独立 worker。请确认是否已启动：

```powershell
python -m requesttool worker
```

### 11.2 为什么能看页面但不能编辑

通常是当前角色没有写权限，最常见的是 `developer` 角色。

### 11.3 为什么 AI 功能没有直接改掉我的用例

这是设计选择，不是 bug。

平台故意把 AI 定位成“建议生成器”和“辅助决策器”，不是直接改写核心资产的自动执行器。这样能降低误改风险，保证落库和执行结果仍然是确定性的。

### 11.4 为什么 AI 测试数据和 AI Mock 应用后看起来没改请求体

因为它们当前写入的是 case metadata，用于保存 AI 产物和后续预执行准备，不是直接覆盖你正在编辑的请求体。

### 11.5 为什么 AI Mock 生成了模板，但执行时没有自动变成运行时 Mock

因为当前版本管理的是 Mock 模板和执行前准备，不是完整的 runtime mock 平台。

### 11.6 为什么环境变量里的 `123` 变成了 number

环境变量按 JSON 字面量解析：

- `123` 会被识别为 number
- `true` 会被识别为 boolean
- `"tenant-a"` 会被识别为 string

如果你希望严格按字符串处理，请显式加引号。

## 12. 当前版本边界

当前版本已经具备可用主链路，但仍建议按 `MVP+ / Beta` 理解。

已知边界包括：

- 默认数据库更偏向本地开发场景
- 历史桌面端导入能力仍然保留，用于平滑迁移
- AI 预执行准备当前是 case-first，不是 suite 级编排
- AI Mock 当前是模板管理，不是运行时 Mock 平台
- AI 最终仍是建议层，不负责替代确定性执行规则
