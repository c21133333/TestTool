# Eazy Test Web 用户手册

## 1. 这份手册解决什么问题

这不是一份“功能清单”，而是一份给真实使用者看的操作手册。

如果你是第一次接触 Eazy Test Web，建议按这份手册的顺序阅读：

1. 先看“快速上手”，完成一条最短可用链路
2. 再看“角色与权限”，确认自己能做什么
3. 最后按“页面说明”和“常见场景”深入使用

如果你想了解项目背景、技术架构、部署方式和工程边界，请继续阅读 [project-overview.md](D:\works\project\ezTest\TestTool\docs\manuals\project-overview.md)。

## 2. 快速上手

### 2.1 入口地址

- Web 页面：`http://127.0.0.1:8000/`
- API 文档：`http://127.0.0.1:8000/docs`

如果前端已经构建完成，后端会直接托管 `frontend/dist`，访问根路径即可进入系统。

### 2.2 使用前确认

第一次使用前，先确认这 4 件事：

1. 你已经有可登录账号
2. 后端服务已经启动
3. 如果要跑套件执行，`worker` 也已经启动
4. 如果要用脚本型处理器，本机可用 `Node.js`

套件执行依赖独立 worker，未启动时，套件任务会停留在排队中：

```powershell
python -m requesttool worker
```

脚本型处理器依赖本机 `node`。如果系统找不到 Node.js，可显式配置：

```env
REQUESTTOOL_NODE_BIN=/absolute/path/to/node
```

### 2.3 管理员初始化

系统不会默认创建弱口令管理员。只有显式开启以下配置时，启动阶段才会自动创建 bootstrap admin：

```env
EAZYTEST_BOOTSTRAP_ADMIN_ENABLED=true
EAZYTEST_BOOTSTRAP_ADMIN_USERNAME=your_admin
EAZYTEST_BOOTSTRAP_ADMIN_PASSWORD=StrongPassword
```

注意：

- bootstrap admin 默认关闭
- 用户密码必须满足最小长度和强度要求
- 生产环境不应启用 bootstrap admin

### 2.4 第一次使用的最短路径

如果你只想尽快跑通一次完整流程，按下面做：

1. 登录系统
2. 进入“工作台”，创建项目
3. 在项目下创建套件
4. 在套件下创建一条 API 用例
5. 进入“环境”，创建一个测试环境并填 `Base URL`
6. 进入“执行”，选择这条用例并发起执行
7. 进入“报告”，预览 HTML 或 JSON 报告

这就是当前版本最顺的主链路。

## 3. 角色与权限

系统当前采用三类角色：

| 角色 | 可见页面 | 可执行动作 |
| --- | --- | --- |
| `admin` | 全部页面 | 登录、项目/套件/用例/环境维护、执行管理、报告查看、审计日志、用户管理 |
| `tester` | 概览、工作台、环境、执行、报告 | 登录、测试资产维护、执行管理、报告查看 |
| `developer` | 概览、工作台、环境、执行、报告 | 以查看为主，不能维护工作台和环境，也不能进入用户管理与审计日志 |

权限边界以当前前端页面和接口控制为准：

- `admin` 和 `tester` 可以维护项目、套件、用例和环境
- `admin` 才能进入“审计日志”和“用户管理”
- `developer` 默认是只读协作角色，可以看，但不能做受限写操作

## 4. 先理解系统里的 4 类核心对象

开始操作前，先把这 4 个概念想清楚：

| 对象 | 作用 | 典型内容 |
| --- | --- | --- |
| 项目 `Project` | 业务或系统边界 | 一个服务域、一个业务线、一个系统群 |
| 套件 `Suite` | 一组可一起维护或执行的用例集合 | 登录链路、订单链路、回归集 |
| 用例 `Case` | 单条可执行 API 测试定义 | Method、URL、请求体、断言、处理器 |
| 环境 `Environment` | 运行上下文 | Base URL、公共请求头、变量 |

一句话理解：

- 项目是容器
- 套件是组织方式
- 用例是最小执行单元
- 环境是运行时上下文

## 5. 推荐操作链路

### 5.1 新建资产

建议顺序：

1. 创建项目
2. 创建套件
3. 创建用例
4. 创建环境

这样可以避免“先写了很多用例，后面又回头补项目和环境”的混乱。

### 5.2 执行验证

验证链路建议这样跑：

1. 先跑单条 `case`
2. 单条通过后，再跑整套 `suite`
3. 生成报告后，再做共享和复盘

原因很简单：单用例问题更容易定位，套件执行更适合做批量验证和回归。

### 5.3 治理动作

如果你是管理员，建议把治理动作放在最后做：

1. 审计日志排查谁改了什么
2. 用户管理补齐协作账号和角色

不要把“治理动作”插在“创建和执行资产”的主链路中间，否则会打断首次使用体验。

## 6. 页面说明

### 6.1 概览

“概览”用于快速判断平台现在处于什么状态，页面会展示：

- 项目数、套件数、用例数、环境数
- 执行成功率、进行中执行数、失败执行数
- 最近执行
- 最新报告

适合在这些时候使用：

- 刚登录，先看当前工作区有没有现成资产
- 团队例会前，快速扫一眼最近执行健康度
- 想确认最近有没有新的报告产出

### 6.2 工作台

“工作台”是测试资产维护中心，包含“项目”“套件”“用例”三个页签。

#### 项目

你可以：

- 新建项目
- 编辑项目名称和描述
- 查看项目下的套件数和环境数
- 删除项目

建议：

- 一个业务域或系统边界对应一个项目
- 项目描述尽量写清服务范围，方便后续导入与协作

#### 套件

你可以：

- 为指定项目创建套件
- 编辑套件
- 删除套件
- 从 Excel 导入测试用例
- 从旧版桌面端 `project.json` 导入历史资产

两种导入方式的差异：

- Excel 导入：适合把现有测试台账快速变成系统用例
- 桌面端导入：适合迁移旧版套件、用例、环境和执行记录

导入前建议：

- 先创建目标项目
- 明确导入内容应该落到哪个项目
- 在迁移前备份原始文件

#### 用例

一条用例由这些部分组成：

- 基本信息：所属套件、名称、Method、URL、描述
- 请求头：结构化 Key-Value 编辑
- 请求体：支持“结构化对象”或“原始 JSON”
- 断言：结构化断言列表
- 前置处理器：请求发送前执行
- 后置处理器：响应返回后执行
- 元数据：分类、优先级、负责人、标签、前置条件、超时和扩展 JSON

请求体填写建议：

- 请求体是普通 JSON 对象时，优先使用“结构化对象”
- 请求体结构复杂，或你希望完整保留原始内容时，使用“原始 JSON”
- “结构化对象”模式只适合 JSON object，不适合数组或其他复杂原始结构

断言当前支持的类型包括：

- `status_code`
- `json_path`
- `response_body`
- `header`
- `response_time`

处理器当前支持的类型包括：

- `set_variable`
- `builtin_function`
- `sleep`
- `jsonpath_extract`
- `regex_extract`
- `fail_if`
- `script`

填写建议：

- 一条用例至少保留 1 条核心断言
- 能用结构化断言表达的逻辑，不要优先塞进脚本
- 只有超出常见字段范围的元数据，才放进“扩展元数据 JSON”

### 6.3 环境

“环境”页用于维护运行上下文。

每个环境包含：

- 所属项目
- 环境名称
- `Base URL`
- 公共请求头
- 环境变量

典型用法：

- 为同一套用例准备“开发 / 测试 / 预发布”多个环境
- 把通用鉴权头放在环境里，而不是重复写进每个用例
- 把会变的值放进变量，减少硬编码

环境变量支持按 JSON 字面量解析，所以不只可以放字符串，也可以放：

- number
- boolean
- object
- array

建议：

- `Base URL` 只放环境域名和公共前缀
- 变量命名尽量稳定，不要频繁改名

### 6.4 执行

“执行”页是运行中心，支持两类执行：

- `case`：单用例立即执行
- `suite`：套件进入 worker 队列执行

你可以在这里：

- 发起执行
- 搜索和筛选执行记录
- 只看失败执行
- 查看执行详情
- 取消套件执行
- 对成功或失败的历史执行发起重试

执行页的关键行为规则：

- 只有 `suite` 且状态为 `pending` / `running` 时可以取消
- `failed` 或 `success` 的执行可以重试
- 当列表中存在 `pending` 或 `running` 的执行时，页面会自动轮询刷新

执行详情里可以看到：

- 执行状态、范围、环境、时间
- 通过项、失败项、通过率
- 错误信息
- 结构化摘要
- 每个执行项的请求、响应、断言结果

建议的排查顺序：

1. 先看执行状态和错误信息
2. 再看失败拆解和重试统计
3. 最后展开具体执行项看请求、响应和断言结果

### 6.5 报告

“报告”页用于集中查看历史执行产物。

当前支持两种报告类型：

- `HTML`
- `JSON`

你可以：

- 按类型筛选报告
- 在侧边抽屉中预览报告
- 在新标签页打开报告
- 下载报告

使用建议：

- 面向业务展示或汇报，优先看 HTML 报告
- 面向问题排查或二次处理，优先看 JSON 报告

### 6.6 审计日志

仅 `admin` 可见。

“审计日志”用于追踪关键写操作，支持：

- 搜索摘要、资源或操作人
- 按动作筛选
- 按操作人筛选
- 按时间范围筛选
- 展开查看详细 JSON

适用场景：

- 排查谁改了什么
- 复盘误操作
- 做基础合规留痕

### 6.7 用户管理

仅 `admin` 可见。

当前页面支持：

- 创建用户
- 设置显示名称
- 指定角色
- 查看用户状态

建议角色分配：

- 平台维护者设为 `admin`
- 测试资产维护和执行人员设为 `tester`
- 只需要查看结果、不负责维护资产的研发成员设为 `developer`

## 7. 常见使用场景

### 7.1 从零开始创建一条 API 用例

1. 进入“工作台 > 项目”，创建项目
2. 进入“工作台 > 套件”，创建套件并归属到该项目
3. 进入“工作台 > 用例”，创建用例
4. 填写 Method、URL、请求头、请求体
5. 配置至少一条断言
6. 如有需要，添加前置/后置处理器
7. 保存后进入“环境”创建测试环境
8. 到“执行”页发起单用例执行
9. 到“报告”页查看结果

### 7.2 批量迁移历史测试资产

1. 先创建目标项目
2. 进入“工作台 > 套件”
3. 如果来源是 Excel，使用“导入 Excel”
4. 如果来源是旧桌面端，使用“导入桌面端项目”
5. 导入完成后检查套件、用例、环境和执行记录是否齐全
6. 抽样发起执行，验证迁移结果

### 7.3 为同一套测试切换环境

1. 在“环境”中创建多个环境
2. 尽量让用例 URL 使用相对路径或与环境协同设计
3. 在“执行”页发起执行时选择环境
4. 用报告对比不同环境下的结果差异

### 7.4 只读角色如何参与协作

如果你的角色是 `developer`，你仍然可以参与这些动作：

- 查看项目、套件和用例结构
- 阅读环境配置
- 查看执行记录与失败详情
- 预览和下载报告

但你不能直接维护资产或发起受限操作。这种设计的目的，是把“协作查看”和“资产改写”分开。

## 8. 常见问题

### 8.1 登录失败怎么办

先检查：

- 账号是否存在
- 密码是否正确
- 用户是否启用
- 是否真的开启了 bootstrap admin 配置

### 8.2 为什么能看到页面但不能编辑

通常是因为当前角色是 `developer`。这个角色默认只能查看，不能维护工作台和环境，也不能发起受限执行操作。

### 8.3 为什么套件执行一直停在排队中

因为套件执行依赖独立 worker。请确认是否已启动：

```powershell
python -m requesttool worker
```

### 8.4 报告能生成，但页面打不开怎么办

优先检查：

- 报告文件是否已生成到 `web_runs/`
- 后端是否正常运行
- 当前登录态是否有效

### 8.5 处理器脚本不生效怎么办

先确认本机存在可用 Node.js，并且 `node` 能被系统找到。必要时可显式配置：

```env
REQUESTTOOL_NODE_BIN=/absolute/path/to/node
```

### 8.6 为什么环境变量里的数字变成了数字类型

因为环境变量编辑器会按 JSON 字面量解析值：

- `123` 会被识别成 number
- `true` 会被识别成 boolean
- `"tenant-a"` 会被识别成 string

如果你希望它严格作为字符串，建议显式加引号。

## 9. 当前版本边界

这套系统已经具备可用主链路，但当前仍应按 `MVP+ / Beta` 理解，而不是最终成熟版。

已知边界包括：

- 默认数据库仍偏向本地开发场景
- 历史桌面端导入能力仍然存在，本质上属于迁移桥接能力
- 报告已经支持在线预览、打开和下载，但报告体验仍有继续产品化空间
- 执行链路已经支持取消、重试、轮询和详情查看，但更强的生产级观测和恢复能力仍在持续完善
