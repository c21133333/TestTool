# Eazy Test Web 用户使用手册

## 1. 这份手册解决什么问题

这不是一份只介绍页面按钮的说明书，而是一份面向真实使用者的工作手册，重点回答 4 个问题：

1. Eazy Test Web 当前能做什么。
2. 它为什么能提升 API 测试效率。
3. 第一次上手、日常回归、失败排查分别该怎么操作。
4. AI 在哪些环节能帮你提速，哪些决策仍然必须由人来拍板。

如果你还想了解项目背景、架构和部署基线，可以继续阅读：

- [project-overview.md](./project-overview.md)
- [environment-governance.md](./environment-governance.md)
- [execution-reliability.md](./execution-reliability.md)
- [observability.md](./observability.md)
- [2026-03-24-ai-copilot-roadmap.md](../plans/2026-03-24-ai-copilot-roadmap.md)

## 2. 产品一句话

Eazy Test Web 是一个面向团队协作的 Web-first API 测试平台。

它把原本散落在个人机器上的测试资产、执行过程、报告产物和 AI 辅助能力统一收口到浏览器中，形成一条可追踪的工作链路：

`项目 -> 套件 -> 用例 -> 环境 -> 执行 -> 报告 -> 复盘`

## 3. 功能总览

### 3.1 核心对象

| 对象 | 作用 | 你会在什么时候用到 |
| --- | --- | --- |
| `Project` | 业务域/系统域的顶层容器 | 按系统、业务线、服务域管理测试资产 |
| `Suite` | 一组可一起维护、一起回归的用例集合 | 按链路、模块、回归集组织用例 |
| `Case` | 最小执行单元 | 编写请求、断言、处理器、元数据 |
| `Environment` | 运行时上下文 | 配置 Base URL、公共 Header、环境变量 |
| `Execution` | 一次真实执行记录 | 查看运行状态、失败项、重试、诊断 |
| `Report` | 执行产物 | 预览 HTML/JSON 报告，做复盘总结 |

一句话理解：

- `Project` 解决“放哪儿”
- `Suite` 解决“怎么组织”
- `Case` 解决“测什么”
- `Environment` 解决“在哪儿测”
- `Execution` 解决“跑得怎么样”
- `Report` 解决“怎么沉淀结果”

### 3.2 页面功能地图

#### 概览

- 查看项目数、套件数、用例数、环境数。
- 查看最近执行、成功率、最新报告等全局状态。
- 适合做每日巡检和快速感知当前工作区健康度。

#### 工作台

- 管理 `Project / Suite / Case`。
- 编辑请求方法、URL、Headers、Body、Assertions、Processors、Metadata。
- 支持 Excel 导入。
- 支持旧版 `project.json` 迁移导入。
- 集成 AI 覆盖扫描、测试点生成、草稿导入、断言建议、测试数据、Mock 模板、AI 预执行准备。

#### 环境

- 管理 `Base URL`、公共请求头、环境变量。
- 让同一套用例在不同环境中复用，而不是把地址和鉴权信息硬编码进每条用例。

#### 执行

- 发起 `case` 即时执行。
- 发起 `suite` 排队执行。
- 查看执行列表、筛选失败项、取消运行中任务、重试历史任务。
- 查看每条执行项的请求、响应、断言结果。
- 对失败执行生成 AI 诊断建议。

#### 报告

- 管理 HTML/JSON 报告。
- 在线预览、下载、在新标签页打开。
- 生成 AI 报告总结，并应用到报告元数据中。

#### 审计日志

- 仅 `admin` 可见。
- 追踪谁在什么时间做了什么操作。
- 适合排查资产变更、导入、AI 应用、执行操作等治理问题。

#### 用户管理

- 仅 `admin` 可见。
- 管理账号、角色、启停状态。

## 4. AI 测试提效

### 4.1 AI 的定位

先讲边界，再讲能力。

Eazy Test Web 里的 AI 是 `Copilot`，不是 `Autopilot`：

- AI 负责提出建议、补全信息、辅助归因、帮助总结。
- AI 不负责替你做最终判定，不直接改写执行结果，不绕过人工确认落库。

这意味着平台强调的是“提效”和“可追溯”，不是“让 AI 直接接管测试”。

### 4.2 AI 提效点总览

| 阶段 | AI 能力 | 入口位置 | 解决什么问题 |
| --- | --- | --- | --- |
| 设计阶段 | 覆盖率扫描 | 工作台 | 找出项目/套件还没测到的维度 |
| 设计阶段 | 测试点生成 | 工作台 | 把覆盖缺口或文档描述转成可审阅测试点 |
| 设计阶段 | 用例草稿生成 | 工作台 | 批量生成待导入的用例草稿 |
| 编写阶段 | 断言建议 | 用例编辑区 | 补齐容易漏掉的断言 |
| 编写阶段 | AI 测试数据 | 用例编辑区 | 快速生成 payload 变体和建议断言 |
| 编写阶段 | AI Mock 模板 | 用例编辑区 | 生成可复用的依赖响应模板 |
| 运行阶段 | AI 预执行准备 | 用例编辑区 | 选择已保存的 test data / mock 参与本次执行 |
| 排障阶段 | AI 诊断 | 执行详情 | 对失败执行做第一轮归因 |
| 汇报阶段 | AI 总结 | 报告详情 | 把技术结果转成业务可读总结 |

### 4.3 为什么这些能力真的能提效

#### 1. 先用 AI 找缺口，再补用例

很多团队的慢，不是慢在“不会写用例”，而是慢在“不知道还缺什么”。

覆盖率扫描和测试点生成先回答“还没测到哪”，再进入生成和编写，能明显减少无效补测、重复造轮子和全是 happy path 的问题。

#### 2. AI 负责补强，不替代最小核心设计

高质量测试用例通常不是 AI 一次性全自动生成出来的，而是：

- 人先写最核心主链路
- AI 再补断言、补边界数据、补 mock 模板

这样做的好处是主测试意图仍由人控制，AI 负责做机械、重复、容易漏的部分。

#### 3. AI 产物先保存，再显式选择参与执行

AI 测试数据和 AI Mock 模板不会静默改写你正在编辑的请求体。

平台采用的是：

1. 先生成并保存 AI 产物到 case metadata。
2. 再在“AI 预执行准备”里显式选择这次要带哪些 variant/template。
3. 执行结果里记录本次命中了哪些准备项。

这让同一条用例可以反复组合试验，不会因为 AI 一次建议把基础用例本体污染掉。

#### 4. 失败诊断和报告总结缩短复盘路径

排查慢，往往不是系统没报错，而是信息太散。

执行页的 AI 诊断会把失败分类、根因假设、下一步建议先做一轮归纳；报告页的 AI 总结会把技术输出压缩成业务和管理层更容易阅读的摘要。这样团队在排障和汇报时会更快进入重点。

### 4.4 AI 使用原则

- 先有人类定义的主链路，再用 AI 扩展。
- 先看原始请求/响应/断言结果，再看 AI 诊断。
- 默认优先“追加应用”，只有确认旧结果质量差时才使用“覆盖应用”。
- AI 建议是候选方案，不是事实本身。

## 5. 快速上手

### 5.1 访问入口

- Web：`http://127.0.0.1:8000/`
- API 文档：`http://127.0.0.1:8000/docs`

如果前端已构建，后端会直接托管 `frontend/dist`。

### 5.2 使用前确认

第一次使用前，建议先确认以下事项：

1. 你已经有可登录账号。
2. 后端服务已启动。
3. 如果要执行 `suite`，独立 worker 已启动。
4. 如果用例包含脚本型处理器，本机可找到 `Node.js`。

Worker 启动命令：

```powershell
python -m requesttool worker
```

如果系统找不到 `node`，可显式配置：

```env
REQUESTTOOL_NODE_BIN=/absolute/path/to/node
```

### 5.3 第一次跑通主链路

建议按下面顺序完成第一次上手：

1. 登录系统。
2. 进入“工作台”，创建一个项目。
3. 在项目下创建一个套件。
4. 在套件下创建一条 API 用例。
5. 进入“环境”，创建测试环境并填写 `Base URL`。
6. 回到工作台，补齐请求头、请求体和最小核心断言。
7. 进入“执行”，先跑单条 `case`。
8. 查看执行详情中的请求、响应、断言结果。
9. 进入“报告”，查看 HTML 或 JSON 报告。

这条路径是当前版本最稳、最容易理解的最小闭环。

## 6. 操作手册

### 6.1 创建测试资产

#### 创建项目

1. 进入“工作台”。
2. 在项目区域点击“新增项目”。
3. 填写项目名称和说明。
4. 保存后，项目会成为后续套件和用例的容器。

#### 创建套件

1. 在工作台切到套件区域。
2. 选择所属项目。
3. 填写套件名称和说明。
4. 保存后，套件会成为批量回归和组织用例的基本单位。

#### 创建用例

1. 在用例区域点击“新增用例”。
2. 选择所属套件。
3. 填写请求方法、URL、描述。
4. 配置 `Headers`、`Body`。
5. 补充 `Assertions`、前后置 `Processors`、Metadata。
6. 保存后，这条用例即可单独执行。

### 6.2 配置环境

1. 进入“环境”页面。
2. 创建环境并填写名称。
3. 配置 `Base URL`。
4. 配置公共请求头和环境变量。
5. 在执行时选择该环境。

建议把以下内容放进环境而不是写死在用例里：

- 服务地址
- 鉴权头
- 租户标识
- 环境差异参数

### 6.3 发起执行

#### 执行单条用例

适合本地验证、快速调试、精确排错。

方式一：

1. 在“执行”页选择 `scope=case`。
2. 选择目标用例。
3. 选择环境。
4. 发起执行。

方式二：

1. 在工作台用例编辑区完成“AI 预执行准备”选择。
2. 直接触发单条 prepared execution。

#### 执行整个套件

适合日常回归和批量校验。

1. 在“执行”页选择 `scope=suite`。
2. 选择目标套件。
3. 选择环境。
4. 发起执行。
5. 在执行列表中观察状态变化。

注意：`suite` 执行依赖独立 worker 消费队列。

### 6.4 查看执行详情

进入执行详情后，重点看 4 个区域：

1. `执行摘要`：先看状态、通过率、失败数。
2. `结构化摘要`：看失败拆解和重试统计。
3. `执行项详情`：逐项看请求、响应、断言结果。
4. `AI 诊断`：在看完原始结果后，再用 AI 辅助归纳。

推荐排查顺序：

1. 先看失败项原始请求和响应。
2. 再看断言失败点。
3. 然后生成 AI 诊断。
4. 最后决定是改用例、改环境、还是排查真实回归。

### 6.5 查看和使用报告

1. 进入“报告”页。
2. 选择目标报告。
3. 可在线预览、下载，或在新标签页打开。
4. 如需面向业务或管理者输出摘要，可生成 AI 总结。
5. 确认摘要可用后，可应用到报告元数据中，形成带摘要的报告资产。

### 6.6 导入历史资产

#### Excel 导入

适合从台账、手工维护列表快速收口到平台。

操作方式：

1. 在工作台选择目标项目。
2. 上传 Excel。
3. 导入完成后抽样检查关键用例。
4. 再补环境、断言和执行验证。

#### 旧版 `project.json` 导入

适合从历史桌面版资产迁移到 Web 体系。

推荐流程：

1. 先创建目标项目。
2. 导入 `project.json`。
3. 抽样执行核心用例。
4. 用报告校验迁移质量。
5. 再用 AI 补齐断言和测试数据。

## 7. AI 功能使用方法

### 7.1 用 AI 做测试设计

适用场景：

- 新项目刚建好，不知道测试覆盖还缺什么。
- 手上有接口文档或 Markdown 描述，想先转成测试点。
- 想先做 test design，再决定哪些点值得落成真实用例。

推荐步骤：

1. 在工作台选定 `Project` 或 `Suite`。
2. 先做“AI 覆盖率扫描”。
3. 阅读 coverage 缺口和建议测试点。
4. 把缺口转成“AI 测试点生成”的提示输入。
5. 审阅测试点列表。
6. 选择有价值的测试点。
7. 基于测试点生成用例草稿。
8. 审核后导入套件。

### 7.2 用 AI 补断言

适用场景：

- 请求已写完，但断言明显偏少。
- 只有状态码断言，缺少关键业务字段断言。
- 想让 AI 补充容易遗漏的结构、Header、JSONPath 校验。

推荐步骤：

1. 先保存用例。
2. 在用例编辑区点击“AI 补断言”。
3. 先看建议列表和差异预览。
4. 优先使用“追加应用”。
5. 若旧断言明显错误，再考虑“覆盖应用”。

### 7.3 用 AI 生成测试数据

适用场景：

- 一条用例需要快速扩展出多个边界/异常 payload。
- 想生成“必填缺失、长度边界、非法枚举、金额边界”等变体。

推荐步骤：

1. 保存用例。
2. 在“AI 测试数据”区域生成 preview。
3. 选择要保留的 variant。
4. 应用到 case metadata。
5. 在“AI 预执行准备”里选择这次执行要携带的 variant。

### 7.4 用 AI 生成 Mock 模板

适用场景：

- 依赖服务不稳定或未就绪。
- 想构造一些不易在线上真实制造的异常响应。

推荐步骤：

1. 保存用例。
2. 生成 AI Mock 模板。
3. 选择要保留的 template。
4. 应用到 case metadata。
5. 在“AI 预执行准备”里选择本次执行要带的 template。

注意：当前版本管理的是 `Mock 模板`，不是完整 runtime mock 平台。

### 7.5 用 AI 预执行准备

这是当前 AI 提效链路里很关键的一步。

它的核心价值不是“改写用例”，而是“把已保存的 AI 产物显式带入本次执行”。

使用方法：

1. 在工作台打开某条已保存用例。
2. 在“AI 预执行准备”中选择测试数据变体。
3. 选择 Mock 模板。
4. 选择环境。
5. 发起 prepared execution。
6. 执行完成后，在执行结果中查看本次 preparation 摘要。

### 7.6 用 AI 做失败诊断

适用场景：

- 执行失败后，需要先做第一轮归因。
- 想快速区分是环境问题、鉴权问题、断言过严，还是更像真实回归。

推荐步骤：

1. 先看执行原始详情。
2. 点击“AI 诊断”。
3. 阅读诊断分类、根因假设和下一步建议。
4. 用 AI 结果辅助排查，而不是直接把它当最终结论。

### 7.7 用 AI 做报告总结

适用场景：

- 需要把技术报告转成更适合业务、研发负责人、项目经理阅读的摘要。

推荐步骤：

1. 打开报告详情。
2. 点击“AI 总结”。
3. 审核 `executive_summary`、`risk_summary`、`recommended_actions`。
4. 确认可用后再“应用总结”。

## 8. 推荐使用方式

### 8.1 从零开始搭一套 API 测试

1. 创建项目。
2. 创建套件。
3. 创建环境。
4. 先手工写 1 到 3 条核心主链路用例。
5. 跑通单条 `case`。
6. 用 AI 补断言和测试数据。
7. 用 AI 覆盖扫描和测试点生成扩展剩余用例。
8. 批量导入草稿。
9. 跑套件回归。
10. 用报告和 AI 总结做复盘。

### 8.2 从历史资产迁移到平台

1. 创建目标项目。
2. 导入 Excel 或旧版 `project.json`。
3. 先抽样执行核心用例。
4. 用报告验证迁移质量。
5. 再用 AI 做断言补强、测试数据扩展和覆盖缺口分析。

### 8.3 做一次高效失败排查

1. 在执行页筛选失败记录。
2. 打开执行详情，只看失败项。
3. 查看请求、响应、断言结果。
4. 生成 AI 诊断。
5. 回到用例、环境或依赖侧修复。
6. 重新执行验证。
7. 在报告页生成 AI 总结，输出复盘结论。

### 8.4 团队协作的推荐分工

- `admin`：负责平台治理、账号管理、审计排查。
- `tester`：负责测试资产建设、AI 使用、执行和报告分析。
- `developer`：负责查看结果、参与问题排查和复盘，不默认承担写操作。

## 10. 常见问题

### 10.1 为什么套件一直停在排队中

因为 `suite` 执行依赖独立 worker。

请确认已启动：

```powershell
python -m requesttool worker
```

### 10.2 为什么我能看页面但不能编辑

通常是当前角色没有写权限，最常见的是 `developer` 角色。

### 10.3 为什么 AI 没有直接改掉我的用例

这是设计选择，不是 bug。

平台故意把 AI 定位成“建议生成器”和“辅助决策器”，而不是自动改写核心测试资产的执行器。这样能降低误改风险，保证执行和落库结果仍然是确定性的。

### 10.4 为什么 AI 测试数据或 AI Mock 应用后，请求体看起来没变

因为它们当前写入的是 case metadata，用于保存 AI 产物和后续预执行准备，而不是直接覆盖你正在编辑的请求体。

### 10.5 为什么 AI Mock 生成了模板，但执行时没有自动变成 runtime mock

因为当前版本管理的是 `Mock 模板` 和 `执行前准备`，不是完整的运行时 Mock 平台。

### 10.6 为什么环境变量里的 `123` 会变成 number

环境变量按 JSON 字面量解析：

- `123` 会被识别成 number
- `true` 会被识别成 boolean
- `"tenant-a"` 会被识别成 string

如果你希望严格按字符串处理，请显式加引号。

## 11. 当前版本边界

当前版本已经具备可用主链路，但仍建议按 `MVP+ / Beta` 理解。

已知边界包括：

- 默认数据库更偏向本地开发场景。
- 历史导入能力仍然保留，用于平滑迁移。
- AI 预执行准备当前是 `case-first`，不是 `suite` 级编排。
- AI Mock 当前是模板管理，不是完整 runtime mock 平台。
- AI 最终仍是建议层，不替代确定性执行规则。
