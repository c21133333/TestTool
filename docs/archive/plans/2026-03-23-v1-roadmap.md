# Eazy Test Web V1 Roadmap

## 1. 背景

当前版本已经完成了从桌面端向 Web-first 形态迁移的主链路：

- FastAPI 后端
- React 管理台
- Project / Suite / Case / Environment 管理
- 单用例执行
- Suite 排队执行与 worker 消费
- HTML / JSON 报告
- 用户、角色、审计日志
- Excel 与桌面 `project.json` / 历史运行数据导入

这说明产品已经通过了“主价值链可行性验证”，更接近 `MVP+ / Beta`，但距离真正意义上的 `v1` 仍有明显差距。

当前差距不在“有没有功能”，而在“有没有产品级稳定性、边界、运维能力与发布纪律”。

## 2. v1 的定义

本 roadmap 对 `v1` 的定义不是“再加更多页面”，而是满足以下四个条件：

1. Web 主链路可以稳定支撑团队日常使用。
2. 默认配置、安全边界、数据库方案、部署方式达到可交付水平。
3. 历史桌面兼容逻辑被明确标记为迁移桥，而不是长期主模型。
4. 团队能够持续发布、回滚、排查问题，而不是依赖作者手工维护。

## 3. v1 Exit Criteria

满足以下条件，可认为达到 `v1.0` 发布门槛：

- 使用 PostgreSQL 或同级生产数据库，且有明确迁移机制。
- 后端、worker、前端有标准部署方式和环境变量清单。
- 默认管理员弱口令被移除，生产环境无开发态 bootstrap 风险。
- 执行链路具备超时、重试、取消、失败定位和基本可观测性。
- 报告、运行数据、数据库备份恢复策略明确。
- 历史导入逻辑有生命周期说明，且不会继续侵蚀主模型。
- CI 能自动完成测试、前端构建和基本启动校验。
- README 与 docs 能支撑新成员接手和环境搭建。

## 4. 路线图设计原则

### 原则 1: 先收口，再扩功能

当前主链路已经够用了，`v1` 不是继续堆新功能，而是收口边界、补工程化、降低运维熵。

### 原则 2: 先解决高风险底座，再优化体验

数据库、安全、部署、执行可靠性属于底座问题，应优先于 UI 精修。

### 原则 3: 迁移能力保留，但停止扩张

Excel、`project.json`、历史 run 报告导入当前仍然必要，但只应作为迁移桥，不应继续演化为长期产品核心。

## 5. 推荐阶段划分

这里不给死日期，只给推荐顺序。若是一个小团队连续推进，可按 4 个阶段执行。

### Phase 1: 底座收口

目标：

- 把数据库、安全、配置、部署从开发态拉到可交付态

### Phase 2: 执行与运维可靠性

目标：

- 让执行链路在失败、并发、异常场景下依然可控、可定位

### Phase 3: 产品化与迁移边界

目标：

- 提升可用性，同时控制遗留兼容面的继续扩张

### Phase 4: 发布与长期维护

目标：

- 建立持续交付、回滚、文档和版本治理能力

## 6. 十大工作流

下面这 10 件事就是从当前版本走到 `v1` 的核心工作流。

---

## Workstream 1. 数据库生产化

### 目标

把默认 SQLite 升级为生产数据库方案，推荐 PostgreSQL。

### 为什么现在必须做

SQLite 适合单机开发和轻量验证，但不适合多人协作、并发写入、长期运维和备份恢复。

### 交付物

- 支持 PostgreSQL 的 `DATABASE_URL`
- 模型迁移机制，例如 Alembic
- 初始化与升级脚本
- 开发 / 测试 / 生产三套环境配置说明

### 完成标准

- 新环境可一键初始化数据库
- 结构变更不再依赖 `create_all`
- 从旧库迁移到新库有最小可行路径

### 依赖关系

- 会影响部署文档、CI 和运维方案

---

## Workstream 2. 安全基线收口

### 目标

移除开发态弱口令和隐式风险，把权限与认证拉到可交付水平。

### 为什么现在必须做

当前默认 bootstrap admin 适合本地开发，但如果直接进共享环境，风险非常高。

### 交付物

- 生产环境禁用默认管理员创建，或要求首次初始化显式提供密码
- 更明确的 token 生命周期策略
- 密码复杂度与账号启停规则
- 关键操作权限矩阵文档

### 完成标准

- 生产配置不存在 `admin / admin123`
- 无认证、越权访问、误配启动这类明显风险
- 角色权限边界可被测试验证

### 依赖关系

- 和部署、用户管理、审计日志联动

---

## Workstream 3. 配置与环境治理

### 目标

让系统具备清晰、可控、可审计的运行配置。

### 为什么现在必须做

从代码上看，当前已经有 `EAZYTEST_` 前缀配置，但环境边界、默认值策略和生产约束还不够完整。

### 交付物

- 完整 `.env.example`
- 环境变量分层说明
- 开发 / 测试 / 生产配置规范
- 必填项与危险默认值检查机制

### 完成标准

- 新环境部署无需翻源码找配置
- 关键配置缺失时启动失败并给出清晰错误
- 不再依赖隐式默认值拼运气

### 依赖关系

- 和数据库、安全、部署、CI 强耦合

---

## Workstream 4. 部署拓扑标准化

### 目标

明确前端、后端、worker 的部署方式和基础运行架构。

### 为什么现在必须做

当前代码已经具备 `backend + worker + frontend/dist 托管` 形态，但还缺标准部署定义，不利于交接和上线。

### 交付物

- 推荐部署拓扑图
- 单机部署方案
- 最小生产部署方案
- 反向代理与静态资源托管说明
- 进程保活策略

### 完成标准

- 团队可以按文档完整拉起一套环境
- worker 不再依赖人工盯守
- 部署行为可重复、可回放

### 依赖关系

- 依赖数据库和配置治理

---

## Workstream 5. 执行链路可靠性

### 目标

让执行系统在排队、取消、失败、卡死、超时等场景下更稳。

### 为什么现在必须做

执行系统是这个产品的心脏。当前已经能跑，但距离“稳定可托付”还差一层工程保护。

### 交付物

- Case / Suite 执行超时机制
- 执行失败分类与可定位错误信息
- worker 异常恢复策略
- 更清晰的取消语义与状态流转
- 必要的并发策略说明

### 完成标准

- 执行异常不会静默吞掉
- 队列卡住时可恢复
- 用户能知道失败原因，而不是只看到失败结果

### 依赖关系

- 和日志、监控、报告展示强相关

---

## Workstream 6. 可观测性补全

### 目标

让系统具备最小可行的日志、指标和排障能力。

### 为什么现在必须做

没有可观测性，就没有生产可维护性。执行失败、导入失败、权限问题都会变成“只能读代码猜”。

### 交付物

- 结构化日志
- 关键业务日志点：登录、导入、执行、取消、重试、报告生成
- 基本健康检查与依赖状态说明
- 最小指标集合，例如执行成功率、失败数、平均耗时

### 完成标准

- 出问题时能通过日志快速定位模块和请求
- 核心任务链路有可追踪记录
- 运维排障不再全靠复现

### 依赖关系

- 贯穿所有工作流

---

## Workstream 7. API 契约与错误模型收口

### 目标

让前后端契约、错误码、分页筛选和响应语义稳定下来。

### 为什么现在必须做

当前 API 已经不少，如果不尽早收口契约，后续改动会越来越贵。

### 交付物

- API 命名与响应规范
- 错误码或错误分类文档
- 分页、筛选、列表查询一致性规范
- 对外使用说明或 OpenAPI 约定说明

### 完成标准

- 前端不再依赖猜测错误文案处理异常
- 主要列表接口风格统一
- 接口变更有明确约束

### 依赖关系

- 和前端体验、测试、文档同步推进

---

## Workstream 8. 前端产品化

### 目标

把当前“可用后台”升级为“能稳定服务团队的产品界面”。

### 为什么现在必须做

现在页面功能已经够多，但体验层还偏工程后台。`v1` 需要的是可理解、可上手、可持续使用。

### 交付物

- 更完整的空状态、加载态、错误态
- 导入结果与执行结果的反馈优化
- 报告查看体验加强
- 关键页面交互收口
- 权限受限场景的明确提示

### 完成标准

- 新用户不看源码也能完成核心操作
- 错误信息可理解
- 报告、执行、导入体验不再像“内部工具半成品”

### 依赖关系

- 依赖 API 契约与执行链路稳定

---

## Workstream 9. 遗留兼容面的退场策略

### 目标

明确哪些历史兼容逻辑继续保留，哪些停止扩展，哪些在 `v1.x` 后删除。

### 为什么现在必须做

兼容层如果没有退出策略，会持续污染主模型和代码结构，最后产品永远停留在“迁移中”。

### 交付物

- 兼容能力清单
- 每项兼容能力的保留期限和用途说明
- 禁止继续扩展 legacy 格式的规则
- `v1.x` 后的清理计划

### 完成标准

- 团队对“迁移桥”和“正式模型”认知一致
- 不再新增桌面时代格式耦合
- 删除计划可执行，而不是口头共识

### 依赖关系

- 和导入、文档、产品策略相关

---

## Workstream 10. CI/CD 与发布治理

### 目标

建立可重复发布、校验和回滚的工程流程。

### 为什么现在必须做

如果没有 CI/CD，当前版本再好，也仍然是“作者本机可跑”。这不叫 `v1`，这叫“手工作坊”。

### 交付物

- CI 检查：pytest、前端 build、基础启动校验
- 发布说明模板
- 版本号策略
- 回滚流程
- 变更清单与发布门禁

### 完成标准

- 每次发布前自动完成关键校验
- 回滚路径明确
- 团队不依赖单人记忆发版

### 依赖关系

- 需要数据库、配置、部署方案先基本稳定

## 7. 推荐执行顺序

推荐顺序不是按“谁容易做”，而是按“谁最能降低系统风险”。

### 第一优先级

1. 数据库生产化
2. 安全基线收口
3. 配置与环境治理
4. 部署拓扑标准化

### 第二优先级

5. 执行链路可靠性
6. 可观测性补全
7. API 契约与错误模型收口

### 第三优先级

8. 前端产品化
9. 遗留兼容面的退场策略
10. CI/CD 与发布治理

## 8. 建议里程碑

### Milestone A: 可交付底座

满足条件：

- PostgreSQL 可用
- 配置清单完整
- 部署文档成型
- 默认弱口令移除

### Milestone B: 可稳定运行

满足条件：

- worker 行为稳定
- 执行异常可定位
- 报告和运行任务可追踪

### Milestone C: 可持续发布

满足条件：

- CI 跑通
- 发布流程明确
- 回滚路径明确
- 迁移边界说明完成

### Milestone D: v1 Ready

满足条件：

- README、部署文档、运维文档可支撑交接
- 主链路用户体验达到可交付水平
- 兼容层边界清晰
- 团队接受该版本进入正式迭代

## 9. 主要风险

### 风险 1: 继续堆功能，忽略底座

后果：

- 看起来功能更多，实际上版本更难上线

### 风险 2: 迁移逻辑无限延期

后果：

- 产品会长期被 legacy 格式绑架

### 风险 3: 把 SQLite 开发体验误当成生产方案

后果：

- 多人环境下出现并发、锁、恢复、备份问题

### 风险 4: 没有 CI/CD 就直接进入频繁迭代

后果：

- 每次发版都靠人工记忆和手工验证，系统熵会快速上升

## 10. 一句话结论

这个项目距离 `v1` 已经不远了，真正缺的不是更多业务功能，而是把“能跑”收口成“能交付、能维护、能发布”。

如果只抓一个核心方向，那就是：

**先把底座工程化，再把迁移边界产品化。**
